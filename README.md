# Feel My Heartbeat

供两人使用的实时互动页面。一端点击，两端同时显示爱心。

项目零依赖，仅使用 Node.js 内置模块。核心文件为 `server.js` 与 `index.html`；
另有 `debug.html`，是独立的只读调试台（`/debug`），仅在排查问题时使用，删除后不影响主页面运行。

调试还有一个 `/test` 入口：页面与代码完全相同，但接入的是服务端内存中的另一个房间 ——
在该房间中的操作不写入 `hearts.json`，也不写入 `history/`，与真实房间中的用户互不可见。

下文命令中的 `<项目目录>` 指 `server.js` 所在的目录。

## 本机需要运行的进程

要让对方能够连接，本机需要同时运行以下两个进程，缺一不可：

| 角色 | 说明 | 命令 | 端口 |
|------|--------|------|------|
| **服务器** | Node 服务本体，负责保存计数、转发消息 | `node server.js` | 本机 `8787` |
| **Cloudflare 隧道** | 将本机 8787 端口暴露到公网，并分配一个 `https://xxx.trycloudflare.com` 地址 | `cloudflared tunnel --url http://localhost:8787` | — |

口令共两个，均配置在项目根目录的 `.env` 中（不纳入版本库）：

| 变量 | 用途 | 未设置时的行为 |
|------|------|-----------|
| `ROOM_KEY` | 主页面进入房间的口令，需要分发给对方 | 回退到默认值 `change-me`，启动时输出警告 |
| `DEBUG_KEY` | `/debug` 调试台专用口令，不对外分发 | 调试台关闭（`/state`、`/history`、`/who` 一律返回 401） |

调试台可以查看 IP、User-Agent、连接明细与全部历史纸条，因此不接受房间口令 ——
仅掌握 `ROOM_KEY` 的用户（包括对方）无法进入该页面。两个口令不应设置为相同值，相同时启动会输出警告。

下文命令中出现的 `123456`、`654321` 均为示例口令，请替换为实际值。

> ⚠️ 当前使用的是**临时隧道（quick tunnel）**，其主要特点是：**每次重启 cloudflared 都会分配一个新的地址。** 重启后需要将新地址发送给对方。
>
> ⚠️ **部署到公网之前必须修改默认口令。**

## 启动

服务器负责数据。修改 `server.js` 之后，或进程异常退出之后，需要重启。

```bash
# 1) 停止旧进程
pkill -f "node server.js"

# 2) 进入项目目录，携带口令启动
cd <项目目录>
ROOM_KEY=123456 DEBUG_KEY=654321 PORT=8787 node server.js
```

启动成功后会输出「Feel My Heartbeat」与版本号，以及累计心跳数和同频次数；
日志中同时打印本机地址与局域网地址。数据保存在同目录下的 `hearts.json` 中，重启不丢失。

访问 `http://localhost:8787`，填写名字与口令即可进入。

**在后台持续运行（关闭终端后不中断）：**

```bash
cd <项目目录>
ROOM_KEY=123456 DEBUG_KEY=654321 PORT=8787 nohup node server.js > server.log 2>&1 &
```

查看日志：`tail -f server.log`（在项目目录下执行）

## 公网访问

推荐使用 Cloudflare Tunnel：免费，无需购买服务器，也无需在路由器上开放端口。
地址无法访问，或服务器重启之后，重启隧道即可：

```bash
# 1) 停止旧隧道
pkill -f "cloudflared tunnel"

# 2) 重新启动，指向本机 8787
cloudflared tunnel --url http://localhost:8787
```

启动后输出内容较多，其中包含一行由框线包围的地址：

```
+--------------------------------------------------------+
|  https://随机单词-随机单词.trycloudflare.com            |
+--------------------------------------------------------+
```

**该地址即为新的访问地址，复制后发送给对方。**

**在后台运行，并将地址记录到文件：**

```bash
cd <项目目录>
nohup cloudflared tunnel --url http://localhost:8787 > tunnel.log 2>&1 &

# 等待数秒后提取地址
sleep 6 && grep -o 'https://.*trycloudflare.com' tunnel.log | head -1
```

**重启 node 不需要重启 cloudflared**，隧道只绑定端口，不绑定进程。

临时隧道每次重启都会更换地址。如需固定地址，可将域名接入 Cloudflare，再创建命名隧道（`cloudflared tunnel create` → `route dns`）。

### 对方的使用方式

1. 确认两个进程均在运行（见下方「运行状态检查」）。
2. 获取当前的 `https://xxx.trycloudflare.com` 地址。
3. 将**地址**与**口令 `123456`** 发送给对方。
4. 对方在手机或电脑浏览器中打开该地址，输入口令即可进入房间。
5. 自己使用相同的地址与口令进入，双方即可连通。

> 房间的连接数上限为 8（`MAX_CLIENTS`），足以覆盖两人反复刷新的场景。超出上限时会断开最久无活动的连接。

## 功能说明

| | |
|---|---|
| 点击 | 两端同时显示爱心。本端为粉色，对端为青色 |
| 长按 | 连续触发。空格键行为相同 |
| 同频 | 双方在 3 秒内先后点击时，两端同时触发金色特效，背景爱心也随之转为金色 |
| 对方离线时 | 点击记录暂存，待对方上线后一次性回放 |
| 纸条 | 支持快捷词与自由输入，在两端屏幕上飘过。服务端留存，可在 `/debug` 调试台查阅 |
| 同时在线时的音乐 | 双方均在线时随机播放 `music/` 中的曲目，一方离线后淡出。两端播放同一首、同一进度 |
| 选歌 | 点击顶栏「选歌」或当前播放条，列出全部曲目。选定后两端同时切换 |
| 播放状态 | ♪ 左侧显示曲名与时间，进度以该区域底色自左向右填充表示 |
| 本端静音 | 右上角 ♫ 仅控制本端音频输出，对端不受影响；再次开启后接入当前播放进度 |
| 背景爱心 | 持续向上飘动。单人在线时仅显示本端的粉色，双方在线时粉蓝各半 |
| 快捷词 | 共 11 个，修改 `index.html` 中的 `QUICK` / `QUICK_MORE` 可以增减 |
| 悬浮窗 | 始终置顶的小窗口，需要 Chrome 或 Edge 116 及以上版本 |

悬浮窗要求安全上下文，仅 `localhost` 与 `https://` 可用，通过 `http://` 访问局域网 IP 时不可用。

快捷词分为两组：`QUICK` 中的三个在悬浮窗内保留，`QUICK_MORE` 中的仅在大窗口显示
（带 `extra` 类，由 `.compact .chip.extra` 隐藏）。悬浮窗宽度仅 200px，
向 `QUICK` 中增加条目会将其撑开，新增条目请加入 `QUICK_MORE`。

## 版本管理

版本号格式为 主版本.次版本.修订号，前后端共用同一个版本号。

**次版本号需要累积多个小更新之后再递增。** 常规的新增功能、缺陷修复、格式调整均只递增修订号，
较语义化版本更为保守。

**版本号不写入 commit title**，改动说明写清楚具体内容即可。

**仅为次版本及以上打 tag**（`v1.1.0`、`v1.2.0`、`v2.0.0`），修订号不打 tag ——
改动通过 commit 查阅即可，无需占用 tag 列表：

```bash
# 仅在递增次版本时执行
git tag -a v1.2.0 -m "..." && git push origin v1.2.0

git tag -n1          # 查看所有已发布版本
```

**版本号写在三处，修改时需要同步更新：**

1. `package.json` 的 `version` 字段（唯一来源，服务端优先读取）
2. `server.js` 顶部的 `let VERSION`（读取 package.json 失败时的兜底值）
3. `index.html` 中的 `const VERSION`

**三道自动检查：**

- **启动时**：服务端读取 `index.html` 比对版本，不一致时在日志中输出警告
- **登录时**：前端通过 `/check` 获取服务端版本，不一致时在登录页拦截，提示「服务端是 X，前端是 Y」
- **重连时**：`welcome` 事件携带服务端版本，不一致时停止轮询，顶栏提示「服务端已更新到 X，请刷新页面」

这三道检查源于实际遇到的问题：更新时只替换了部分文件，或者未重启服务，表现为各类难以定位的连接故障。

第三道检查针对的场景是：**页面长时间保持打开，其间服务端完成了升级。** 登录检查只在进入时执行一次，
无法覆盖该场景；旧页面会带着旧代码继续轮询，可能无法处理新增的事件，表现为
「对方已在线且已发送消息，但本端无任何响应」，而服务端日志与 `history/` 中的记录一切正常。
修改 `index.html` 之后，两端均需刷新页面（`Ctrl+Shift+R`）。

改动记录在 `CHANGELOG.md` 中。

## 排查

**查看服务端当前的连接情况**

```bash
curl "http://localhost:8787/who?key=你的调试口令"
```

返回连接数、各连接的名字、连接时长、静默时长、是否有挂起的请求，
以及该连接的入口地址、浏览器类型与页面版本 ——
在线名单中出现无法确认的连接时，依据这几项即可识别对应的设备与页面。

**清空统计**（调试数据积累过多时）

```bash
curl -X POST "http://localhost:8787/reset?key=你的口令"
```

**测试房间 `/test`**

在地址后追加 `/test`（`http://localhost:8787/test`），返回的是**完全相同的页面** ——
同一份 `index.html`、同一套代码，区别仅在于它接入的是服务端内存中的另一个房间：

- 统计不落盘、纸条不写入 `history/`，服务端重启后该房间即被清空
- 与真实房间完全隔离：在 `/test` 中点击心跳、发送纸条，对端不会有任何感知，
  在线名单中也不会增加连接
- 顶栏左侧显示金色的「测试房间」标签，页面四周为淡金色边框，标题同步改为
  「测试房间」，以便区分当前所处的房间
- 音乐仍共用 `music/` 目录（只读，播放不会产生任何写入）

**一键同频模式**（仅 `/test` 提供）

`/test` 顶栏增加一个「同频模式」按钮。启用后，服务端向该测试房间加入一个
不依赖浏览器的模拟客户端（名称为「测试的 TA」）：

- 该客户端计入在线名单，因此页面立即进入「双方在线」状态 —— 背景爱心、音乐播放、
  同在计时均正常启动
- 点击心跳后，它会在同频窗口内跟随点击一次，两端同时触发金色特效 ——
  真实房间中难以复现的同频效果，在此可以直接触发
- 长按连续触发时它不会逐次跟随，每 2.5 秒响应一次，避免同频特效连续触发
- 再次点击按钮将其移除

也可以通过命令行操作，真实房间不允许调用（返回 403）：

```bash
curl -X POST "http://localhost:8787/bot?key=你的口令&room=test&on=1"
```

**调试台**

在浏览器中打开 `http://localhost:8787/debug`，手动输入**调试口令**（`.env` 中的 `DEBUG_KEY`，
与房间口令是两个独立的口令，房间口令在该页面无效）。该页面每次访问都需要输入：
主页面的登录状态不生效，地址栏中的 `?key=` 参数也不被接受（来自旧书签的参数会在进入页面时从地址栏清除）。
未设置 `DEBUG_KEY` 时该页面不可访问，服务端启动时会输出相应提示。

调试台与主页面是**两个完全独立的页面**，且为只读：不加入房间、不计入在线人数、
不消费暂存的心跳与纸条，页面上也没有任何可以修改房间状态的操作 —— 使用它进行观察，
不会在对端增加连接，也不会影响统计数据。

单页展示服务端当前的完整状态，每 2 秒刷新一次（可暂停）：

- **在线连接**：连接数、各连接的设备与浏览器、页面版本、连接时长、静默时长、
  是否有挂起的请求、队列积压条数、入口地址、来源 IP、设备号、连接 id
- **最近被断开的连接**：id、原因（`replaced` 被同设备顶替 / `stale` 页面版本不符）、发生时间 ——
  用于定位「在线设备数异常增加」「本端被断开」等情况
- **计数**：今日与累计的分人计数、同频次数、上一次心跳的来源与时间（以及是否仍在同频窗口内）、
  存档文件大小与写入时间、Node 版本与内存占用
- **暂存队列**：等待投递给对方的心跳数与纸条
- **纸条记录**：按日期查看当天全部纸条，查看最新一天时自动跟进（见「聊天记录」）
- **music 目录**：服务端识别到的曲目
- **服务端参数**：连接数上限、同频窗口、纸条长度上限、超时时间等代码中的常量
- **原始 /state**：完整的 JSON 数据

顶栏的「看：真房间／test 房间」用于切换观察对象 —— 在 `/test` 中产生的数据，
需要切换到 test 房间才能看到。

命令行获取同一份数据：`curl "http://localhost:8787/state?key=你的调试口令"`，
追加 `&room=test` 查看测试房间。`/who`、`/reset` 同样支持该参数。

**常见问题**

| 症状 | 可能原因 | 处理方式 |
|---|---|---|
| 对方反馈地址无法打开 | 隧道地址已变更（曾经重启），或隧道未运行 | 按「公网访问」重新启动，发送新地址 |
| 可以打开但无法进入房间 / 提示口令错误 | 口令需要完全一致 | 确认口令为 `123456` |
| `/debug` 输入口令后无法进入 | 该页面校验的是 `DEBUG_KEY`，房间口令在此无效；也可能根本未设置 | 检查启动日志中是否有未设置 `DEBUG_KEY` 的警告，在 `.env` 中补充后重启 |
| 可以打开但无实时同步、心跳无响应 | 服务器（node）未运行 | 按「启动」重新启动 |
| 登录页提示版本不一致 | 只替换了部分文件，或者未重启 node | 三处版本对齐后重启 node |
| 双方互相不可见 | 名字填写相同 —— 服务端按名字识别用户，同名会被视为同一人 | 使用不同的名字 |
| 修改 `server.js` 后未生效 | node 需要重启才会加载新代码 | 重启 node；修改 `index.html` 无需重启服务端，对方刷新页面即可 |
| 持续显示重连中 | 服务器未运行，或者隧道已断开 | 检查两个进程 |
| 延迟偏高 | 隧道线路本身的往返时间 | 改用命名隧道或 VPS 直连 |
| 数据丢失 | 未在同一目录下启动 | 检查 `hearts.json` 是否存在，以及是否在同目录启动 |

## 通信

采用 HTTP 长轮询，共四个接口：

- `POST /join` 进入房间并获取 id
- `GET /poll` 拉取消息，有消息时立即返回，无消息时最多挂起 25 秒
- `POST /send` 发送消息
- `POST /leave` 关闭页面时立即下线

上述接口均支持一个可选的 `room=test` 参数，携带时进入内存中的测试房间
（`/test` 页面发出的每个请求都会携带该参数），不携带时为真实房间。

另有若干需要口令的辅助接口，除 `/reset` 与 `/bot` 之外均为 GET 只读：
`/state` 返回服务端当前的完整状态（`/debug` 页面即由其渲染）、
`/who` 查看在线情况、`/reset` 清空统计、`/history` 获取聊天记录、
`/music/list` 获取曲目清单、`/music/file` 提供音频流（支持 Range，可以拖动进度，兼容 Safari）、
`/bot` 在测试房间中加入或移除模拟客户端。

**各接口校验的口令有明确区分：** `/state`、`/history`、`/who` 属于调试台一侧，
仅校验 `DEBUG_KEY`；其余接口（`/check`、`/join`、`/poll`、`/send`、`/leave`、
`/music/*`、`/reset`、`/bot`）校验 `ROOM_KEY`。`/check` 支持一个可选的 `for=debug` 参数，
携带时改为校验调试口令 —— 调试台页面的登录即使用该方式。
此外 `/debug` 为调试台页面，`/test` 为测试房间页面（返回的是 `index.html`）。

详细的演进过程见 `CHANGELOG.md` 中的早期迭代记录。

## 同时在线时的音乐

音频文件放在 `music/` 目录下，直接放入即可，新增曲目无需重启（每次请求清单时都会重新读取目录）。
双方均在线时随机选择一首播放，一首结束后自动接续下一首，一方离线后逐渐淡出。

**两端播放的是同一首、同一进度。** 播放哪一首、从何时开始，均以服务端的记录为准
（见 `server.js` 中的「同一首歌，同一处」）：页面获取到的是「该曲目已播放的毫秒数」，
收到后以本地时钟继续推进，无需两端同步时钟，误差仅为一次网络往返。
中途加入的一端直接接入当前进度，无需等待下一首。

**选歌**：点击顶栏「选歌」按钮，或点击当前播放条，会列出 `music/` 中的全部曲目。
选定一首后，双方从该曲目开头同步播放；「换一首」为随机重新选择。
单人在线时不播放音乐，清单中的条目不可点击，服务端也不接受该操作。

**右上角 ♫ 仅控制本端的音频输出**，对端不受影响；再次开启后接入当前播放进度。
这与「音乐停止」是两回事 —— 是否播放仅由双方是否同时在线决定。

支持的扩展名：`.mp3` `.m4a` `.aac` `.ogg` `.oga` `.opus` `.wav` `.flac` `.webm`。
其中 mp3 与 m4a 兼容性最好，各浏览器均可播放。以 `.` 开头的文件会被跳过。

音频文件不纳入版本库（`.gitignore` 中仅放行 `music/README.md`）。

```bash
# 服务端识别到的曲目数
curl "http://localhost:8787/who?key=你的调试口令" | grep 曲目数

# 曲目清单
curl "http://localhost:8787/music/list?key=你的口令"
```

浏览器要求页面存在用户交互之后才允许播放音频。正常从登录页点击「进入」即满足该条件；
若被拦截，♫ 处会提示「点一下心跳，音乐就接上」，点击大爱心即可恢复。

Chrome 另有一项限制：**页面处于后台标签页时不会下载下一首曲目**，
因此该端会停留在当前曲名上，切回前台之后才开始播放 —— 切回时会直接接入
对端当前的播放进度，不会从头播放。手机锁屏、切换 App 的行为相同。

当前播放的曲目显示在 ♪ 左侧：曲名（不含扩展名）与时间；进度不单独绘制进度条，
而是将该区域底色自左向右填充。未在播放时不显示。

顶栏在窄屏（≤560px）下无法容纳四项内容，因此在手机上：在线名单使用简短形式
（「TA 03:21」）、总时长隐藏并仅保留已播放时间、`悬浮窗` 按钮不显示
—— 手机浏览器不支持 documentPictureInPicture，点击后只会提示「不支持」。

## 聊天记录

纸条保存在 `history/` 目录下，一天一个文件，文件名为当天日期：

```
history/20260727
```

每行一条 JSON（JSON Lines），追加写入；服务端不将其读回内存，记录增多也不会占用内存：

```
{"t":1785123319008,"name":"chris","text":"miss you"}
```

`t` 为 Unix 毫秒时间戳。选择存储时间戳而非可读时间，是因为其无歧义：排序、计算时长、
转换时区均依赖该值，需要展示时再做转换。

**查看方式**

打开 `/debug` 调试台的「纸条记录」区域：上方选择日期，下方按
`yymmdd 时:分:秒　名字　内容` 列出。查看最新一天时自动跟进，
查看历史日期时不刷新；单日记录达到数千条时仅渲染最后 300 条，避免页面卡顿。

```
260727 14:26:01  chris  miss you
```

也可以使用命令行。接口会在 `t` 之外额外返回一个转换后的 `time` 字段，
文件中不存储该字段：

```bash
# 查看有记录的日期
curl "http://localhost:8787/history?key=你的调试口令"

# 查看某一天
curl "http://localhost:8787/history?key=你的调试口令&date=20260727"
# {"t":1785123319008,"time":"260727 11:35:19","name":"chris","text":"miss you"}
```

删除记录直接删除对应文件：`rm history/20260727`。`/reset` 仅清空统计，不影响记录。

> `history/` 与 `hearts.json` 同样列在 `.gitignore` 中，不纳入版本库。
